# ОЗ — отслеживание заявок

Настольное Rust-приложение для контроля новых заявок в MSSQL и работы с
внутренним XMPP/Miranda-контуром.

## Возможности

- подключение к MSSQL Server и базе `rd_all`;
- выполнение SQL-запроса из отдельного файла;
- периодический фоновый опрос заявок;
- проверка признака завершенного согласования `por_neisp`;
- уведомление выбранного пользователя в Miranda;
- всплытие окна при появлении нового набора заявок;
- команда click-to-call через внутреннюю АТС;
- настройка XMPP-сервера, JID отправителя, JID АТС и цели звонка;
- локальный SQLite-аудит просмотренных заявок.
- виртуальный SIP-телефон с автоматическим ответом на первый этап дозвона.
- ожидание подтверждения от АТС о подключении целевого абонента к bridge перед
  воспроизведением голосового оповещения;
- read-only проверка pfSense REST API v2 и подсчет firewall rules.
- автодозвон через текущий XMPP-командный маршрут при появлении нового набора
  необработанных заявок.

## MSSQL

Основной запрос находится в [sql/remote_work_requests.sql](sql/remote_work_requests.sql).
Он должен возвращать поля `num1`, `ot_kogo`, `date_z`, `date_n`, `time_n`,
`date_k`, `time_k`, `prich` и `por_neisp`.

## Сопутствующая эксплуатационная документация

Поэтапное ТЗ для нового развертывания прокси-сервера закрытого контура Банка
с CentOS на Debian находится в
[docs/TZ_CLOSED_CONTOUR_PROXY_CENTOS_TO_DEBIAN.md](docs/TZ_CLOSED_CONTOUR_PROXY_CENTOS_TO_DEBIAN.md).
Документ не относится к узлам `vds3`, `gw`, `gw2` и не содержит секретов.

Ожидаемая рабочая база:

```text
server=tcp:srv-db,1433;database=rd_all;...
```

Строка подключения передается через переменную окружения
`MSSQL_CONNECTION_STRING` или вводится в GUI. Пароли не записываются в TOML.

## GUI

Запуск без аргументов открывает окно приложения:

```sh
cargo run -- gui
```

В GUI настраиваются MSSQL, периодичность опроса, XMPP и параметры звонка.
Пароли сохраняются в системном Credential Manager. По умолчанию включен
фоновый опрос с интервалом 60 секунд.

В отдельном меню «pfSense» можно включить pfSense REST API v2, указать URL и
API-ключ и выполнить проверку. Таймаут запроса настраивается в секундах
(по умолчанию 60, допустимый диапазон 5–300). Ключ хранится только в Credential Manager и
передается только заголовком `X-API-Key`. На текущем этапе OZ выполняет два read-only
запроса: `/api/v2/system/restapi/version`, постраничного чтения
`/api/v2/firewall/rules` и `/api/v2/firewall/schedules`;
для правил используется интерфейс `openvpn`, соответствующий странице
`firewall_rules.php?if=openvpn`; правила фильтруются локально после чтения
страницами по 50 записей. OZ оставляет только включённые правила типа
`pass`, у которых связанное расписание имеет `active=true`; это соответствует
зелёному индикатору на странице. Изменение
правил, OpenVPN-пользователей и конфигурации pfSense не выполняется.

При ручной проверке OZ также получает заявки из MSSQL и сопоставляет поле
`ot_kogo` с префиксом имени пользователя в описании правила. Русские ФИО
нормализуются в формат «фамилия_инициалы»: например, `Рачков Илья Игоревич`
сопоставляется с `rachkov_ii_syk83`.

Кнопка «Обновить кэш разрешений» сохраняет активные разрешающие правила в
`pfsense-rules-cache.json` рядом с программой. Фоновая обработка SQL использует
только этот кэш; кэш старше 3600 секунд считается недействительным.
Согласованные заявки при обработке автоматически фиксируются в локальном
SQLite-аудите как обработанные, после чего GUI сверяет их с этим кэшем и
показывает разрешенный или запрещенный доступ. Заявки с незавершенным
согласованием повторно остаются в очереди; ранее пропущенные заявки могут быть
обработаны после изменения статуса согласования.

Если сертификат pfSense подписан внутренним или самоподписанным CA, укажите в
поле «CA-сертификат pfSense» путь к сертификату CA в формате PEM или DER.
Проверка TLS при этом не отключается: сертификат сервера и его имя должны
оставаться корректными.

Для закрытой доверенной среды можно включить опцию «Пропустить проверку
TLS-сертификата (только закрытая сеть)». По умолчанию она выключена. При
включении OZ отключает проверку цепочки доверия и имени сертификата только для
соединения с pfSense; используйте эту настройку только в изолированной сети.

«Быстрый отчет» после формирования показывает количество обработанных заявок и
список обработанных заявок в формате «номер — фамилия заявителя».

Автодозвон настраивается в меню «Действия». При включенном флажке OZ отправляет
команду `Позвонить <цель>` после нового XMPP-уведомления. Цель берется из поля
«Цель звонка», а повторное появление того же отпечатка заявок вызов не повторяет.

Для click-to-call используется сообщение вида `Позвонить <цель>`, которое
отправляется на JID АТС. Целью может быть внутренний номер, имя рабочей
станции или JID сотрудника. Источник звонка определяется АТС по XMPP-ресурсу
рабочей станции. Для виртуального телефона используйте учетную запись
`oz@dns.sevnb.ru` и ресурс `oz`: АТС сопоставляет его с номером `1000`.
Диалплан и настройки АТС при этом менять не требуется. JID `pbx@dns.sevnb.ru`
остается получателем команды звонка.

Для работы виртуального телефона в GUI включите раздел «Виртуальный
SIP-телефон», укажите сервер АТС, номер `1000` и Secret endpoint-а. Secret
хранится в Credential Manager. OZ регистрирует SIP endpoint в фоне, принимает
первый вызов автоматически и не требует физического телефонного аппарата.

В этом же разделе можно включить локальное голосовое сообщение. Если поле
«Файл сообщения WAV» пустое, OZ формирует фразу «Количество необработанных
заявок - N штук, номера: ...» локальным Windows Speech
API и передает ее через RTP после
автоответа. Внешние TTS-сервисы не используются. Также можно указать собственный
несжатый PCM WAV: 16 бит, mono, 8 или 16 kHz.

Если необработанных заявок нет, голосовое сообщение и XMPP-уведомление содержат
только фразу «Необработанных заявок нет».

Для динамического голосового сообщения на рабочем месте обязательно должен быть
установлен локальный русскоязычный голос Windows, например Microsoft Irina
Desktop. Установка выполняется в «Параметры → Время и язык → Речь → Голоса».
Интернет при воспроизведении не требуется: синтез выполняется локально через
Windows Speech API. Если русский голосовой пакет не установлен, используйте
подготовленный PCM WAV-файл или установите пакет до запуска OZ.

Несекретные параметры можно подготовить из
`gui-settings.example.toml`; скопируйте его в `gui-settings.toml` и укажите
JID получателя уведомлений.

Фоновый опрос использует скользящий период: по умолчанию последние 30 дней до
текущей даты. Глубина выборки настраивается в поле «Глубина выборки, дней» или
параметром `poll_lookback_days` в секции `[requests]`. Даты вычисляются на SQL
Server при каждом опросе.

## CLI

Одноразовая проверка заявок:

```sh
cargo run -- process-requests --config config.toml
```

Отчет за один день (опорная дата включается в период):

```sh
cargo run -- report --period day --date 2026-09-01 --config config.toml
```

Отчет за неделю: семь календарных дней, заканчивающихся указанной датой:

```sh
cargo run -- report --period week --date 2026-09-01 --config config.toml
```

Отчет выводит строки `OZ_REQUEST` только с номером заявки и статусом:
`processed` — в MSSQL нет неисполненных поручений (`por_neisp=0`), `waiting` —
есть неисполненное поручение (`por_neisp<>0`). Локальный SQLite-аудит OZ не
подменяет статус исполнения из MSSQL.

Для необработанных заявок основной обработчик дополнительно выводит строки
`OZ_PENDING_REQUEST num=... requester=...`. Поле `requester` берется из
`rtrim(d.pole4)` и показывает, кому требуется доступ.

Для обычного запуска без консольного окна используйте собранный `oz.exe`.

## Сборка

```sh
cargo build --release
```

Windows-пакет публикуется в GitHub Releases.

## Безопасность

- не храните пароли в `config.toml`, `gui-settings.toml` и Git;
- используйте отдельную учетную запись MSSQL с минимальными правами;
- XMPP-пароль хранится только в системном хранилище учетных данных;
- текущий XMPP-режим рассчитан на доверенный внутренний маршрут.
