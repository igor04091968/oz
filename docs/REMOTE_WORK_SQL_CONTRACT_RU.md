# SQL-контракт заявок на удаленную работу

Исходный запрос находится в `sql/remote_work_requests.sql`.

Он извлекает заявки из `docum`/`potok` за период подачи заявок и возвращает
сырой бизнес-набор, а не готовые команды pfSense.

## Поля

| Поле | Смысл |
|---|---|
| `date_z` | дата заявки |
| `num1` | номер заявки |
| `ot_kogo` | от кого заявка |
| `date_n` | начальный день удаленной работы |
| `time_n` | период времени в начальном дне |
| `date_k` | конечный день, если заявка не на один день |
| `time_k` | период времени в конечном дне |
| `prich` | причина заявки |
| `por_neisp` | есть неисполненные поручения |

## Важная правка периода

Оригинальное условие `between @d1 and @d2` для `datetime` включает только
значение `@d2` ровно в `00:00:00` и может потерять заявки за остальную часть
последнего дня.

В проекте используется half-open интервал:

```sql
d.date1 >= @d1
and d.date1 < dateadd(day, 1, @d2)
```

## Следующий контракт

Для управления pfSense нужен следующий слой трансформации:

- определить, какие заявки разрешают доступ;
- отфильтровать `por_neisp = 0`, если неисполненные поручения должны блокировать
  изменение доступа;
- нормализовать периоды `date_n/time_n/date_k/time_k` в конкретные временные окна;
- сопоставить заявителя `ot_kogo` с IP, alias, пользователем VPN или группой;
- построить idempotent desired operations: `rule_key`, `action`, `method`,
  `path`, `body_json`, `desired_hash`.

Пока этот слой не задан, приложение не должно применять изменения к pfSense
автоматически.
